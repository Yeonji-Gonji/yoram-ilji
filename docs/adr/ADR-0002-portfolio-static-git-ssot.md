# ADR-0002: 포트폴리오 콘텐츠의 정본을 Notion 에서 Git 으로 옮기고 블로그만 Notion 에 남긴다

- 날짜: 2026-11-10
- 상태: 채택
- 관련: `src/content/portfolio/`, `src/services/portfolio.api.ts`, `src/types/portfolio.type.ts`, `public/portfolio/`, [ADR-0001](ADR-0001-notion-api-rate-limit-build.md)

## 배경

포트폴리오 목록·상세는 빌드 시 Notion 포트폴리오 데이터소스를 읽어 정적 생성했고, 본문 이미지와 커버는 `/api/notion-image` 프록시를 거쳐 서빙했습니다. 이 구조에서 문제가 셋 드러났습니다.

빌드가 외부 서비스에 매여 있었습니다. Notion 공개 API 한도는 통합당 평균 3 req/s 라서 ADR-0001 의 간격 제한과 재시도로 눌러 두었지만, 포트폴리오 16건은 메타 조회 외에 케이스마다 블록 트리를 재귀로 읽기 때문에 요청 수가 가장 많은 축이었습니다. 콘텐츠를 한 글자도 바꾸지 않은 커밋에서도 배포가 Notion 의 응답에 좌우됐습니다.

이미지는 만료되는 URL 이었습니다. Notion 파일 커버와 본문 이미지 블록은 약 한 시간 뒤 만료되는 S3 주소라, 정적 페이지에 박아 둘 수 없어 요청마다 프록시가 Notion 을 다시 호출하는 구조였습니다. 포트폴리오 한 페이지를 여는 데 이미지 수만큼 외부 왕복이 생기고, Notion 쪽 장애가 그대로 화면의 깨진 이미지가 됩니다.

같은 내용을 세 곳에서 관리하고 있었습니다. 이력서·포트폴리오 정본, 개인 Notion 의 포트폴리오 데이터베이스, 그리고 둘을 맞추기 위한 대조 문서가 따로 있어, 수치 하나가 바뀌면 세 곳을 모두 고쳐야 했습니다. 실제로 Notion 쪽에는 갱신이 밀린 수치(섹션 336·블록 5,528·32페이지)가 본문과 어긋난 채 남아 있었습니다.

블로그는 사정이 다릅니다. 글은 주 단위로 늘어나고 모바일에서도 쓰므로 Notion 의 편집 경험이 그대로 필요합니다. 포트폴리오는 분기에 한 번 고치고, 고칠 때마다 이력서와 함께 손보며, 바뀐 내용을 PR 에서 검토할 수 있어야 합니다. 변경 빈도와 검토 필요성이 정반대입니다.

## 검토한 대안

1. 지금 구조를 유지하고 Notion 호출만 더 줄입니다. 빌드 시간은 나아지지만 만료 이미지와 삼중 관리는 그대로 남습니다.
2. 포트폴리오도 Notion 에 두되 빌드 때 이미지를 내려받아 정적 파일로 굽습니다. 이미지 문제는 풀리지만 빌드가 여전히 Notion 에 매이고, 내용 변경이 PR 에 남지 않습니다.
3. 블로그는 Notion CMS 로 두고 포트폴리오만 Git 안의 정적 데이터와 로컬 이미지로 옮깁니다. (채택)
4. 블로그까지 전부 Git 으로 옮깁니다. 글 작성 경험이 나빠지고 모바일에서 쓸 수 없습니다.

## 결정

대안 3을 채택합니다.

포트폴리오 정본은 `src/content/portfolio/<slug>.ts` 열여섯 파일이고, 각 파일이 `PortfolioItem` 타입의 값 하나를 내보냅니다. 노출 순서는 `src/content/portfolio/index.ts` 의 배열 순서이며 상세 페이지의 이전·다음도 이 순서를 따릅니다. 본문 블록 모델은 실제로 쓰는 여섯 가지(제목·문단·목록·콜아웃·표·이미지)만 두고 `src/types/portfolio.type.ts` 에 정의합니다. 타입이 붙은 모듈이라 수치나 구조가 어긋나면 `tsc` 가 먼저 잡습니다.

이미지는 Notion 에서 전량 내려받아 webp 로 변환하고 `public/portfolio/<slug>/` 에 둡니다(커버 16장 + 본문 53장, 합계 약 5.8MB). 본문 이미지 블록은 실제 파일 크기를 함께 저장해 `next/image` 에 넘기므로 레이아웃이 밀리지 않습니다. 포트폴리오 경로에서 `/api/notion-image` 호출은 0건이고, 프록시 라우트 자체는 블로그가 계속 쓰므로 남겨 둡니다.

조회 함수는 `src/services/portfolio.api.ts` 한 곳입니다. 호출부(홈·목록·상세·`sitemap`·`llms.txt`)가 서버 컴포넌트라 `async` 시그니처는 유지하되, 내부는 외부 호출 없이 배열을 걸러 반환합니다. `src/lib/config.ts` 의 `portfolioDataSourceId` 와 Notion 포트폴리오 서비스는 지웠습니다.

## 결과

- 포트폴리오 16건이 Notion 호출 없이 정적 생성되는 것을 빌드로 확인했습니다. 프리렌더된 HTML 열여섯 장에 `/api/notion-image` 와 Notion S3 주소가 각각 0건이고, 이미지 69개가 전부 `/portfolio/...` 경로입니다.
- 회귀는 단위 테스트가 지킵니다(`src/services/__tests__/portfolio.api.test.ts`). 케이스 수·slug 유일성, 모든 이미지 경로가 `public/` 아래에 실제로 존재하는지, 카테고리 필터와 대표 정렬, 이전·다음의 양 끝 처리까지 검사합니다. 이미지 파일 하나를 옮기면 테스트가 실패하는 것을 확인했습니다.
- 콘텐츠 수정이 PR 에 남습니다. 수치를 고치면 diff 로 보이고, 이력서와 함께 한 PR 에서 검토할 수 있습니다.
- 대신 글처럼 포트폴리오를 모바일에서 고칠 수는 없습니다. 분기 단위로 손보는 문서라 이 비용을 받아들입니다.
- 되돌릴 경우의 비용은 Notion 포트폴리오 서비스를 복구하고 데이터소스 ID 를 설정에 되돌리는 정도입니다. Notion 데이터베이스 자체는 지우지 않았습니다.
- 이미지를 더하거나 케이스를 추가할 때는 `public/portfolio/<slug>/` 에 webp 를 두고 정본 파일에 블록을 적습니다. 원본 해상도가 크면 가로 1600px 기준으로 줄입니다.
